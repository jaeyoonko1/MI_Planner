# VOC — 사용자 의견·불편·요청함

> 사용자가 말한 의견을 **VOC 관리 담당**이 정리해 기록한다. **작업을 고를 때 flow보다 먼저 본다** (`AGENTS.md` 작업 선택 절).
> 처리가 끝나면 `상태`를 `완료`로 바꾼다. 커밋 SHA는 이 파일에 새로 적지 않고 리뷰 기록에만 남긴다(기존 해시는 이력으로 보존). 지우지 않는다. 같은 내용이 `project_flow.html`의 "VOC" 단계에도 있으니 둘을 함께 갱신한다.

## 쓰는 법
- 한 건 = 한 줄. ID는 `V-001`부터 순서대로, 한 건 = 한 세션, 커밋 메시지는 `[V-001] 설명`.
- **우선순위 1~5** — **1이 가장 급함**(쓰기 막힘·데이터 위험·핵심 흐름), 5가 가장 여유. 사용자가 직접 준 번호가 원본이며 `추정`은 사용자가 정하지 않아 정리 담당이 매긴 것.
- **분류**: `버그`(있어야 할 동작이 안 됨) · `개선`(있는 기능을 더 낫게) · `기능추가`(없던 기능)
- 상태: `대기` · `진행` · `완료` · `보류`(사유 기재)

## 항목 상세
### V-014 · V-011 재설계: 이슈는 에픽·유형 등 어느 수준으로든 바뀌는 호환 객체
- 분류: **개선**(V-011 구현이 요구와 다름) · 우선순위: **1 (추정)** · 영역: 구조·이슈 계층·이슈 상세 · 크기: **M~L** · 상태: **진행** · V-011(완료)은 이력으로 두고 추가 요구는 여기서 추적.
- **구현 상태**: 세션 A 데이터 모델·API 및 기존 화면 호환 검증. 세션 B 세 보기의 공통 추가 시트·수준 관리·단축키와 자유 배치 검증. 세션 C 한 번 클릭으로 여는 상세창·수준과 상위 편집·구조 실행 취소 및 새로고침 검증.
- **사용자 원문**: "지라처럼 이슈를 추가하면 얘가 바로 에픽이 될 수도 있고 유형이 될 수도 있고 서로 호환이 되는 객체야. 근데 지금은 이슈/그 외로 처리되는 것 같아. 분류 기준이면 고정이라 그렇다 쳐도, 자유인데 왜 갑자기 그룹밖에 추가가 안 돼? 에픽이나 유형도 클릭하면 옆에 창이 튀어나오면서 수정할 거 수정해야지."
- **코드 확인(2026-11-25)**: 사용자 지적이 **대체로 맞음**.
  1. 수준은 별도 정의 표(`issue_levels`, 마이그레이션 013)이고 맨 아래 '이슈'는 `level_id = NULL`인 특수 값이다. "이슈 vs 그 외(수준)" 이원 구조라 Jira처럼 모든 이슈가 같은 객체에서 종류만 바뀌는 모델이 아니다. 수준 이름·순서 수정은 별도 '계층 편집' 화면을 거치고, 규칙 `rank(자식) ≤ rank(부모)`가 수준 바꾸기를 제한한다(D-48).
  2. "이슈 추가" 창은 `issues` 보기에서만 수준·상위 선택이 되고(structissue.js), 분류 기준·자유 배치에서는 분류 없이 최상위 또는 해당 그룹에만 만든다. 분류 기준의 그룹 행은 분류 값이라 에픽처럼 못 만든다("그룹 추가"는 별개 기능).
  3. 에픽·상위 수준 헤더를 눌렀을 때 옆 상세창으로 모든 항목을 수정하는 흐름이 사용자 기대만큼 연결돼 있는지는 **구현 시 확인**(현재 더블클릭·Enter로 상세 열기, 단일 클릭 동작 미확인).
- **기대 동작**:
  1. 이슈는 하나의 객체이며 수준(에픽·유형 등)은 그 이슈의 속성이다. '이슈'만 특수한 NULL이 아니라 다른 수준과 같은 취급으로, 언제든 수준을 바꿀 수 있고 자식은 보존한다(규칙 충돌 시 안내 후 선택).
  2. 구조의 모든 보기(분류 기준 포함)에서 어느 수준이든 바로 추가한다. 분류 기준 보기가 고정이면 그 한계를 화면에 명시한다.
  3. 에픽·유형 등 모든 수준의 행을 클릭하면 옆에 상세창이 열려 이름·수준·상위·내용을 바로 수정한다.
- **수용 기준**: 이슈를 만들어 에픽→유형→이슈로 수준을 바꿔도 값·자식·일지 연결 유지 → 각 보기에서 추가 → 행 클릭으로 옆창 수정이 구조에 즉시 반영 → 새로고침 후 유지. 가짜 데이터로 검증.
- **설계안 (Opus, 2026-11-25)** — 참고: Tempo Structure의 추가(위/아래/하위)·Enter 계열 단축키·"임시 그룹은 이슈가 아님"·마지막 작업 되돌리기 개념만 차용. 보드·스프린트·저장 보기 공유는 넣지 않는다. 새 결정은 **D-49**(D-48의 'NULL=이슈'와 '규칙 하나'를 대체, D-48 본문은 이력으로 두고 첫 줄에 "→ D-49로 일부 대체" 표기).
  1. **단일 객체 모델 (수준 = 이슈의 평범한 속성)**
     - 열 이름은 `tasks.level_id` 그대로(테이블 재작성 없음). '이슈'도 `issue_levels`의 실제 행이 되고, 모든 이슈는 항상 수준 하나를 가진다. UI 용어는 계속 **수준**.
     - `migrations/014_issue_level_unify.sql`: ① `issue_levels`에 `is_default INTEGER NOT NULL DEFAULT 0` 추가 ② `('이슈', 0, 'issue', 'blue', is_default=1)` 행 삽입 ③ `UPDATE tasks SET level_id = <그 id> WHERE level_id IS NULL` ④ 트리거 2개 — `AFTER INSERT ON tasks WHEN NEW.level_id IS NULL`, `AFTER UPDATE OF level_id ON tasks WHEN NEW.level_id IS NULL` → 기본 수준으로 채움. 트리거 덕분에 일지 승격·CLI·복사·**옛 휴지통 스냅샷 복원(level_id NULL)**도 코드 수정 없이 안전. 013의 `ON DELETE SET NULL`은 남지만 수준 삭제는 앱이 먼저 이슈를 옮긴 뒤 지우므로 발동하지 않고, 발동해도 트리거가 기본 수준으로 채운다.
     - `rank`는 **표시 순서일 뿐**: 형제 정렬(수준 높은 순 → 번호), 추가 창 기본값, 칩 순서에만 쓴다. `_renumber`는 '이슈' 행 포함 전체를 n-1…0으로 다시 매긴다. '이슈'도 이름·모양·색·순서 변경 가능.
     - **계층 규칙 완화**: 부모·자식 수준 조합 제한 없음. 서버가 거부하는 것은 **순환(자기 자신·자기 하위를 상위로)** 과 없는 수준뿐. `check_placement`의 rank 비교·`violations()`·순서 변경 409를 제거한다. 자식 수준이 부모보다 높으면 행·상세창에 작은 `역순` 표시(⤴ 모양 + 글자, 색만으로 구분 금지)만 하고 막지 않는다.
     - 수준을 바꿔도 **제목·값·상위·하위·일지 연결·페이지는 그대로**(모두 task id에 걸려 있고 수준은 열 하나). 하위는 따라 바뀌지 않는다.
     - 기각: ⓐ rank 규칙 유지 + "하위도 함께 바꾸기" — 사용자가 원한 '호환 객체'가 아님. ⓑ 수준별 허용 상위 표 — 1인 도구에 과설계. ⓒ `tasks` 재작성으로 NOT NULL·FK 변경 — 위험 대비 이득 없음(트리거로 충분).
  2. **수준 관리 (계층 편집 화면 밖에서도)**
     - 수준 칩 줄(추가 창·상세창·계층 편집 공용 컴포넌트, `structissue.js`의 `levelChips()`) 끝에 **`+ 새 수준`** 칩 → 그 자리에서 이름 입력, Enter 저장(현재 고른 칩 바로 위 순서에 생성, Esc 취소).
     - 칩 우클릭/Shift+F10(V-010 `registerContext`): **이름 바꾸기**(칩이 입력칸으로) · **위로/아래로** · **기본 수준으로**(★ 표시) · **삭제…**(사용 이슈 수와 "N개 이슈는 '○○'(으)로" 미리보기 후 확인).
     - 수준 삭제: 그 이슈들은 바로 아래 수준으로(맨 아래면 바로 위로) 이동, 기본 수준이면 기본도 그쪽으로 넘김, **마지막 1개는 삭제 불가**. 기존 `structure_trash` `kind:"level"` 기록·복원 그대로.
     - 기존 '계층 편집' 시트는 유지(모양·색 고르기, 분류 값 가져오기). '이슈' 행도 일반 행으로 보여 주고 `levels.length + 1` 고정 표시는 없앤다.
  3. **추가 흐름 (모든 보기에서 같은 시트)**
     - `openAddIssueSheet`가 모든 모드에서 **제목 · 수준 칩(+ 새 수준) · 위치**를 받는다. 모드별 '위치'만 다르다.
       - `issues`: 상위 이슈 경로 칩 + `다른 상위…`(기존 `openParentSheet`) + `최상위`.
       - `fields`: 들어갈 분류 값 칩(읽기 전용, `빼기` 가능) + 선택 사항 `상위 이슈 지정…`.
       - `free`: 들어갈 그룹 경로 + 선택 사항 `상위 이슈 지정…`(자유 배치는 계층을 그리지 않으므로 저장만 하고 "이슈 계층 보기에서 보여요" 안내).
     - 기본값: 수준 = **항상 기본 수준 '이슈'**(사용자 확정 2026-11-25), 수준 칩에서 즉시 변경. 하위 추가만 부모 바로 아래 수준을 미리 선택. '계속 추가' 유지.
     - 진입점: 히어로 `이슈 추가` · 행 우클릭 메뉴 **같은 위치에 추가(Ctrl+Enter)** · **하위 이슈 추가(Shift+Enter)** · free 모드만 **위에 추가 / 아래에 추가**(수동 순서가 있는 곳만; issues는 수준→번호 자동 정렬이라 위/아래 의미 없음). fields·free의 Shift+Enter는 "그룹 안에 추가"와 같다.
     - **분류 기준 안내**: fields 모드에서 모드 칩 아래 한 줄 힌트 "이 보기의 묶음은 **분류 값**이에요. 이슈가 아니라서 상위·하위는 '이슈 계층' 보기에서 바꿔요." (닫기 가능, 보기 설정에 기억). 묶음 행은 기존 분류 아이콘 + 이슈 번호 없음으로 이슈 행과 구분. 묶음 안에 추가하면 그 경로의 분류 값이 새 이슈에 들어간다(현재 `assignProps` 재사용).
  4. **옆 상세창 (기존 `inspector.js` 드로어 확장, 새 창 만들지 않음)**
     - 구조 화면에서 **행 한 번 클릭 = 선택 + 상세창 열기/전환**. 포커스는 트리에 남아 ↑↓로 옮기면 창 내용이 따라 바뀐다(120ms 지연 갱신). `openInspector(id, { focus: false })` 옵션 추가. Enter = 상세창 제목칸으로 포커스, Esc = 트리로 복귀(한 번 더 Esc = 창 닫기). 제목 인라인 수정은 F2 또는 **이미 선택된 행의 제목 다시 클릭**(Finder식). Shift/Ctrl 클릭은 선택만(창은 "N개 선택됨" 요약, 일괄 편집은 범위 밖).
     - 편집 항목(위→아래): **머리 줄에 이슈 번호 옆 수준 선택**(눌러서 펼치는 칩 목록, 사용자 요구) · 제목 · 수준 칩(공용 컴포넌트, 머리 줄과 같은 컴포넌트) · **상위**(경로 표시, `바꾸기…`/`해제`) · **하위 N개**(목록 링크 + `하위 추가`) · 상태·납기·요청자 · 분류 칩 · 메모 · 페이지. 저장은 지금처럼 항목별 즉시 PATCH → 구조 트리 즉시 다시 그림.
     - 수준 바꾸기: 확인창 없이 즉시 적용 + 토스트 "에픽 → 이슈로 바꿨어요 · 되돌리기". 하위 중 새 수준보다 높은 것이 있으면 칩 아래에 "하위 2개가 이 수준보다 높아요(역순) — 그대로 둬도 돼요" 안내만.
     - 분류 값 묶음·자유 그룹 행 클릭: 상세창에 **값 카드**(이름·분류명·이슈 수, `이름 변경`·`이 값으로 이슈 추가`·`삭제…`, 기존 `renameGroup`/`requestDelete` 재사용). 이슈 상세와 섞이지 않게 머리에 "분류 값" 배지.
     - 레이아웃: 1280px 이상은 표를 밀어내고(선택 행이 가려지지 않음) 1024px은 겹침, 시안 `prototype_final.html`의 드로어 폭·색 토큰을 따른다.

### V-011 · Jira식 이슈 계층으로 전환: 구조에서 모든 수준의 이슈 직접 추가·수정·삭제
- 분류: **개선**(추가·삭제 동작 누락 포함) · 우선순위: **1 (추정)** — 사용자가 현재 구조를 Jira처럼 활용할 수 없어 핵심 애자일 업무 흐름이 막힌다고 보고함. · 영역: 업무 구조·이슈 계층·분류 관리·이슈 상세 · 예상 크기: **L** · 상태: **완료** (커밋은 아래 완료 표, 결정 D-48).
- **목적**: 애자일 방식으로 일할 수 있도록 업무 구조의 이슈 생성·계층·편집 경험을 Jira에 최대한 가깝게 개선한다. 아래 요구는 분리 VOC를 만들지 않고 **한 건(V-011)**으로 처리한다.
- **사용자 보고**: 현재는 구조에서 원하는 상위 항목을 바로 만들기 어렵고 분류 관리에 값을 하나씩 등록해야 한다. 분류 삭제도 되지 않는다. 삭제 불가의 실제 원인과 범위는 구현 착수 시 확인한다.
- **핵심 요구**:
  1. 업무 구조에서 이슈를 바로 추가한다. 에픽·유형·그 외 사용자 정의 수준 모두 이슈 단위로 취급하여, 특정 계층만 별도 분류 값으로 만들어야 하는 흐름을 없앤다.
  2. 예를 들어 `프로젝트`, `스터디`, `업무`, `결혼준비`를 에픽 수준의 항목으로 만들고 싶으면 분류 관리 화면을 거치지 않고 구조 화면에서 직접 추가할 수 있다. 이 이름들을 고정된 기본 분류로 강제하지 않는다.
  3. 구조의 에픽·유형 등 모든 수준의 항목을 수정·삭제할 수 있어야 한다. 기존 분류 삭제 불가 문제도 같은 VOC 범위에서 조사·해결한다. 기존 휴지통·되돌리기 원칙을 지키며, 하위 이슈가 있는 항목의 삭제·이동 처리를 설계하여 데이터 유실을 막는다.
  4. 이슈의 에픽/상위 소속을 `프로젝트` 등으로 변경하면 구조의 해당 헤더 아래로 바로 반영되어야 한다. 이슈 상세의 값과 구조의 부모·자식 관계가 일치해야 한다.
  5. 헤더를 `에픽 헤더`로 할지 `유형 헤더`로 할지는 미정이며, 사용자는 후자 쪽을 선호한다. **`유형`이라는 용어 자체도 임시**이므로 확정 명칭이나 고정 계층으로 간주하지 않는다. 이슈의 종류·계층 수준과 이슈 제목/상위 소속의 구분은 설계에서 명확히 한다.
- **수용 기준**: 구조에서 위 예시의 상위 이슈와 하위 이슈 생성 → 이슈 종류/수준·상위 소속 수정 → 헤더·계층 즉시 반영 → 각 수준 삭제 및 되돌리기 → 새로고침/재시작 후 관계 유지까지 하나의 흐름으로 검증한다. 기존 이슈·분류·일지 연결은 보존하거나 명시적인 이관 방안을 마련한다.
- **설계 시 확인**: Jira에 가깝게 만드는 구체적인 동작과 헤더 명칭은 이 요구를 기준으로 정리한다. 보드·스프린트 등 사용자가 이번에 구체적으로 요청하지 않은 기능의 추가를 자동으로 확정하지 않는다.
- **처리 결과 (2026-11-24, D-48)**: 상위 수준도 `tasks` 행(이슈)이고 계층은 `parent_task_id`. 수준(에픽 등)은 `issue_levels`(마이그레이션 013)로 정의하며 이름·모양·색·순서를 구조의 '계층 편집'에서 바꾼다. 구조의 기본 보기 = **이슈 계층**(분류 기준·자유 배치는 그대로 선택 가능). **헤더 명칭**: 고정 문자열을 두지 않고 헤더 행 = 이슈 제목 + 수준 배지로 표시, 기본 수준 이름은 `에픽`(이슈 상세의 기존 분류 `유형`과 같은 이름이 둘 생기지 않게). 계층 편집에서 `유형`으로 바꾸면 그대로 반영(마이그레이션 불필요). **분류 삭제 불가 원인**: 서버 삭제 API는 정상. 구조 화면이 분류 기준 그룹 행의 삭제를 막고('분류 관리에서 정리') 분류 관리는 쓰는 값이 있으면 '보관'만 해서 사용자는 지울 수 없다고 느낌 → 분류 기준 보기의 그룹 행(분류 값)을 Delete/F2로 바로 삭제·이름 변경(값만 지우기/이슈도 삭제, Ctrl+Z 복원). 기존 분류 값은 그대로 두고, '분류 값을 상위 이슈로 가져오기'로 명시적으로 이관한다.
